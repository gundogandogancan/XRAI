# XRAI Vault — Threat model v1.13 (P03-05A: T53 consent & interaction authority, T24/T42 amended with PRE-01 ordering; P03-04bH2: T52 global deletion invariant at every entry point; P03-04bH: T51 restore identity & provenance trust, T41/T49 amended; P03-04b: T49 backup provenance & rollback, T50 attachment chunk integrity, T41/T44 amended with GATE 1 ledger binding; P03-04H filesystem atomicity & durability gate: T47–T48, T45 amended; P03-04 store implementation: T39–T46 TESTED at library level, P03-03H hardening T44–T46 + amended T41–T43, P03-03 design rows T39–T43, … + P03-00F device launch, monotonic cache, rotation serialization, 2026-10-20)

**Scope:** the on-device personal vault (encrypted records of birth data, names, optional family data, psychometrics, journals, goals, evidence, consent receipts) and the optional user-held encrypted backup. **Out of scope here:** UI, network broker, model router, StoreKit (own threat models later). **Status:** design + library-level tests; **no device verification, no independent security review yet.** Nothing in this document claims the vault is unbreakable (constitution §83: "No 'unbreakable' promise").

## Assets (constitution §59)
A1 date of birth, exact birth time/place · A2 legal/chosen names · A3 parent names, sibling order (third-party data, high sensitivity) · A4 psychometric answers · A5 journals, private guide history · A6 goals/Future Self, evidence artifacts · A7 derived results (charts, traces) · A8 consent receipts and audit trail · A9 cryptographic keys (DEKs, device KEK, recovery key) · A10 the portable backup file.

## Trust boundaries
B1 process boundary of the app (other apps, extensions, keyboards, clipboard) · B2 OS boundary (lock screen, Data Protection classes, iCloud/iTunes backup) · B3 device boundary (lost/stolen phone, new device) · B4 user boundary (the user is the only key holder; XRAI operates no server for personal data) · B5 content boundary (PDF/web/book excerpts fed to a local model are untrusted data).

## Residual risks stated honestly
- P03-03 (2026-10-20) added T39–T43 as DESIGN rows only; none is implemented or tested; see `docs/status/P03_03_THREAT_AND_NEGATIVE_TEST_PLAN.md` for the N1–N20 chain.
- P03-03H (2026-10-20) amended T41–T43 and added T44–T46 after independent review; acceptance tests enumerated in `docs/status/P03_04_NEGATIVE_TEST_ACCEPTANCE_MATRIX.md`.
- P03-04 (2026-10-20) implemented `XRAIVaultStore` and moved T39–T46 to TESTED at library level (macOS + hosted runs in the ledger). The app does not link the store yet; nothing here is SECURITY_REVIEWED or an OS boundary.
- P03-05A (2026-10-20) reconciled the P03-03 consent design with the accepted decisions, fixed the PRE-01 authorization-ordering oracle and the PRE-02 transitive gap, shipped the versioned purpose registry, the immutable consent chain persisted in the store, the InteractionGate and synthetic consent/restore-risk screens; F-UX-5 closed by measurement. Still not SECURITY_REVIEWED; the app does not persist personal data.
- P03-04bH2 (2026-10-20) closed F-P04BH-01 (deleted identity recreated through ordinary writes — reproduced, then enforced by one policy at every entry point, incl. replay, recovery and reads), removed `releaseQuarantined`, and opened the performance/recovery debt register.
- P03-04bH (2026-10-20) closed the three findings of the P03-04b review (Bloom resurrection, unauthorized envelope write, caller-controlled provenance) and the six additional checks; two more defects were found by the new tests themselves (idempotent ledger append hid re-deletion of a compacted id; the quarantine registry was not released for ids activated by journal replay).
- P03-04b (2026-10-20) closed LEDGER_ONLY_ROLLBACK (journal v2 ledger binding, sticky distrust), shipped backup body v3 with two-phase restore reconciliation and chunked attachments at library level; attachments are not yet part of backups; nothing is SECURITY_REVIEWED.
- P03-04H (2026-10-20) fixed two P0 findings of the first independent code review (T47 exclusive creation, T48 ignored durability results) and the neighbouring defects found in the GATE 3 audit (ledger-only rollback accepted, admission partial on stale key version, temp cleanup before the writer lock, reads after close). Durability remains a best-effort contract over Apple-documented calls; no power-loss testing exists.
- Keys live in process memory while in use; a compromised OS or a debugger can read them.
- A device with passcode removed or a jailbroken device weakens Keychain guarantees.
- A user who loses both backup and recovery key loses the data. This is intended.
- The production `KeychainKeyProvider` exists and is tested on a macOS host with a real Keychain and Secure Enclave, but **not on a physical iPhone**; nothing is persisted yet because no store layer exists.
- The `ConsentAuthority` is a port; its production implementation (own encrypted store, audit trail, UI) is future work.
- No independent security review or penetration test has happened. Statuses are library TESTED, not SECURITY_REVIEWED.
